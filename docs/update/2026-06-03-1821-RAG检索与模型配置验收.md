# Change Note: RAG 检索、模型连通测试与记忆降噪

## 1. What Changed

本轮把知识库检索从“展示命中片段”推进到“面向用户输出答案”的闭环，并补齐了配置、前端状态和会话记忆治理几处容易让用户误判系统不可用的点。

主要变化包括：

- RAG 搜索新增 `document` 文档检索模式，用户明确查资料、标题、简历、课件、材料时会强制检索知识库。
- RAG 搜索结果增加 LLM 汇总回答，失败时才降级为可读的 Markdown 摘要。
- 知识库文档列表和上传任务展示 `chunk_count`，用户能看到文档实际被切成多少子区块。
- 上传文件构建知识库增加浮动状态球，切换页面后仍能看到上传/解析/入库进度。
- Settings 的 LLM 预设增加模型连通测试，支持聊天模型、向量模型、OCR、Rerank 等用途。
- Knowledge Graph 前端类型和关系做中文展示，后端/客户端过滤明显无意义实体和关系，降低 `0/1/10` 这类噪声进入展示层的概率。
- conversation-intelligence-service 在写入 pending memory candidate 前增加二次过滤，避免无关小记忆和 system prompt 类噪声频繁入库。

这是一次功能修复 + 用户体验修复 + 接口扩展 + 生成代码更新。

## 2. Why This Change Was Needed

之前的问题不是单点 bug，而是多个链路的“用户可见反馈”不足：

- Adaptive RAG 看到 `融媒体中心面试简历` 这类短查询时，容易按“让我帮你写简历”理解成 direct answer，而不是“去知识库找这个文档”。
- 知识库上传成功后，前端只看到文档状态，看不到真实 chunk 数；大文件异步解析时，用户切页面后也不知道后台还在跑。
- RAG 命中结果只是片段列表，用户还要自己把片段拼成答案，这不符合“检索增强问答”的使用预期。
- 模型配置保存后没有连通测试，用户不知道 API Key、BaseURL、模型名到底是哪一个出错。
- 会话智能归档如果过度相信 LLM 提炼结果，会把低价值候选也写进 memory-service 的 pending 区，长期会污染记忆召回。

新的设计把“强制查文档”“返回最终答案”“显示分块数量”“模型连接自检”“记忆候选降噪”都放在对应责任层中处理，而不是让用户自己猜。

## 4. Core Flow After The Change

### 文档检索

```text
用户输入查询
  -> 前端选择“文档检索”
  -> api-gateway 调用 rag-service Search
  -> rag-service 强制 mode=document、Retrieve=true
  -> Hybrid / 文档检索召回 chunks
  -> Rerank / CRAG / Self-RAG 继续参与
  -> LLM 根据命中内容生成最终回答
  -> 前端展示最终回答 + 命中来源
```

### 模型连通测试

```text
用户填写或选择 LLM 预设
  -> POST /settings/llm-profiles/test
  -> api-gateway settings handler
  -> settings-service Kitex RPC
  -> 根据 usage_type 选择测试端点
      chat/general/agent/rag_router -> /chat/completions
      embedding -> /embeddings
      ocr -> /layout_parsing
      rerank -> /rerank
  -> 返回 ok、msg、latency_ms
  -> 前端展示测试结果
```

### 会话候选记忆

```text
conversation-intelligence-service 处理归档任务
  -> 拉取会话窗口
  -> LLM/规则提炼 summary/decision/task/topic/memory_candidate
  -> filterMemoryCandidates 二次过滤候选记忆
  -> 摘要/主题进入 RAG
  -> 只有高价值候选进入 memory-service pending 区
```

## 5. Key Code Concepts

### 文档检索模式

`document` 模式不是另一套向量库，而是 RAG Search 的明确用户意图。它告诉 Router：用户现在就是要查知识库，不要因为问题很短或像标题就跳过检索。

这解决了 `融媒体中心面试简历` 被误判成“请帮我写一份简历”的问题。

### chunk_count

`chunk_count` 是用户判断文档是否被正确切片的第一层证据。它统计的是 child chunk 数，不是 parent chunk 数。检索通常命中 child chunk，再回源父 chunk 或摘要作为上下文。

### LLM 汇总答案

RAG 命中片段只是证据，不是最终答案。`synthesizeAnswerWithLLM` 会把 query、命中 chunks、图谱节点和 CRAG 状态组织成 prompt，让模型生成可直接阅读的回答。模型不可用时，才使用 fallback 摘要。

### 模型用途

Settings 里的 LLM profile 现在不只服务聊天模型，还覆盖：

- `agent`
- `general`
- `embedding`
- `ocr`
- `rerank`
- `rag_router`
- `translation`

不同用途测试的 HTTP payload 不一样，所以不能只用 chat completions 测所有模型。

### 候选记忆降噪

记忆不是聊天记录。聊天归档可以有摘要和主题块，但长期记忆必须更克制。`filterMemoryCandidates` 会综合置信度、重要性、内容长度、长期价值信号和去重结果，只保留前 5 条高价值候选。

## 6. Important Implementation Details

- `mode=document` 会绕过 Adaptive Router 的 direct 路线，确保用户主动选文档检索时一定查知识库。
- Adaptive Router 的规则增加标题/材料/简历/课件等查询特征，规则能确定时不再把判断交给 LLM Router。
- RAG 文档列表中的 chunk 数来自 MySQL child chunks 聚合，不依赖 Milvus 返回结果。
- 上传状态球使用前端本地状态保存任务进度，适合当前 api-gateway 内存任务模型；网关重启后历史任务仍不可恢复。
- 模型连通测试不会回显 API Key，只返回测试是否成功、错误信息和耗时。
- OCR 测试当前使用一个轻量远程图片 URL 做最小请求；真实文档 OCR 仍由文档解析链路调用。
- Rerank 测试使用 query + 两段短 documents，验证 endpoint、key、model 基本可用。
- 记忆候选过滤发生在写 artifacts 前，因此前端看到的 memory_candidate 也是过滤后的版本。

### 功能验收建议

RAG：

- 上传一份 Markdown 或 docx，确认文档列表显示 `子区块 N`，N 应大于 1。
- 用“文档检索”搜索文档标题，例如 `融媒体中心面试简历`，应看到路线为检索，并返回最终回答和来源。
- 同一问题分别跑“文档检索 / 混合检索 / 知识图谱”，比较来源是否合理。

Web Search：

- 搜索一个需要实时信息的问题，例如某软件最新版本。
- 结果应包含搜索摘要或抓取正文整理后的回答。
- 官方页面可访问时优先使用官方/高可信来源。

Memory：

- 在会话中明确表达长期偏好，例如“以后回答 Go 问题请先给复杂度，再讲实现”。
- 归档后应进入 pending memory candidate。
- “好/收到/测试/system prompt”这类内容不应进入 pending memory。

Conversation Intelligence：

- 对一个活跃会话手动或定时创建 digest job。
- 检查产物是否有 summary、decision、task、topic。
- 检查摘要/主题是否进入 RAG，候选记忆是否进入 memory pending。

Knowledge Graph：

- 上传包含服务、表、Topic、API 的项目文档。
- 图谱不应出现大量 `0/1/10`、文件页码、图片名作为实体。
- 前端应使用中文类型/关系，并能按类型、关系、社区过滤。

Settings 模型测试：

- 在系统设置中新增或选择一个 LLM 预设。
- 点击“测试连接”。
- chat/agent/general 应测 `/chat/completions`，embedding 测 `/embeddings`，OCR 测 `/layout_parsing`，rerank 测 `/rerank`。
