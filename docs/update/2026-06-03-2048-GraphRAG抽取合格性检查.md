# Change Note: GraphRAG 抽取合格性检查

## 1. What Changed

本次继续收紧知识图谱入库质量：

- GraphRAG 抽取结果必须至少包含一条非 `RELATED_TO` 的强关系，否则整段结果不入图谱。
- 最终入库实体必须参与有效关系，孤立实体会被丢弃。
- 模型一次输出过多关系时，只保留最多 6 条高质量关系。
- 连接后的实体最多保留 8 个，避免一个 chunk 抽出过大的噪声子图。
- 普通文档栏目词，例如“个人经历、工作经历、项目经历、教育背景、求职目标、自我评价”等，不再作为知识图谱实体。
- 新增测试覆盖：孤立实体、纯 `RELATED_TO` 图谱、模型超量输出、普通教学样例。

## 2. Why This Change Was Needed

知识图谱不是“实体列表”，也不是“关键词云”。如果模型只抽出一堆名词，但没有明确关系，这些节点对 GraphRAG 查询没有多少帮助，还会让前端画布变得很乱。

所以现在的合格标准变成：

```text
至少两个实体
  + 至少一条强关系
  + 关系有证据
  + 实体参与关系
  + 不是纯 RELATED_TO 拼出来的弱图
```

这会让图谱规模变小，但更像真正可用的知识结构。

## 3. Files Changed

- `internal/rag-service/service/service.go`: 增加 `graphExtractResultQualified`、`capGraphRelations`、普通文档栏目实体过滤，并调整 `filterGraphExtractResult` 的最终入库门槛。
- `internal/rag-service/service/service_test.go`: 增加图谱合格性相关测试，覆盖孤立实体、弱关系、超量输出和示例词过滤。

## 4. Core Flow After The Change

```text
LLM / 规则抽取 entities + relationships
  -> 过滤明显噪声实体
  -> 过滤低置信关系、无证据关系、类型不合理关系
  -> 判断是否有非 RELATED_TO 强关系
  -> 只保留参与有效关系的实体
  -> 限制每块最多 6 条关系、8 个实体
  -> 写入 GraphRAG 图谱表
```

## 5. Key Code Concepts

**强关系**

强关系是指 `CALLS`、`WRITES`、`DEPENDS_ON`、`CONSUMES` 等能表达明确动作或结构含义的关系。纯 `RELATED_TO` 只能说明“相关”，不能支撑一个可靠子图。

**孤立实体**

孤立实体是没有任何有效关系连接的节点。它更像关键词，不适合进入知识图谱。RAG chunk 和摘要可以承载这类信息，图谱只保留结构化关系。

**超量裁剪**

LLM 有时会过度抽取。代码层限制单个 chunk 最多保存 6 条关系和 8 个实体，避免一次模型输出污染整张图。

## 6. Important Implementation Details

- `graphExtractResultQualified` 要求至少有一条非 `RELATED_TO` 关系。
- `filterGraphExtractResult` 会先验证关系，再反推保留参与关系的实体。
- `capGraphRelations` 会优先保留非 `RELATED_TO` 且置信度更高的关系。
- 简历/文档栏目词不会进入图谱；这类内容更适合用普通 RAG 检索和文档摘要回答。

## 7. How To Verify

已执行：

```bash
go test ./internal/rag-service/service
```

建议手动验证：

```text
1. 用普通简历、课程材料重新入库，确认不会生成“个人经历、求职目标、Teacher、Linux”等噪声节点。
2. 用项目技术文档重新入库，确认服务、表、事件主题之间的 CALLS / WRITES / CONSUMES 等强关系仍然保留。
3. 在知识图谱页面选择单个文档，确认图谱更稀疏但关系更可读。
```
