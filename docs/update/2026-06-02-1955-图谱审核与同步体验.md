# Change Note: 图谱审核与同步体验

## 1. What Changed

本次更新继续补齐路线图里的几块 MVP 缺口：

- `knowledge-service` 新增图谱候选审核表、Kitex RPC、api-gateway 路由和前端审核入口。
- IM 前端新增上线同步流程、离线索引读取、未读数读取和最近消息本地缓存。
- 前端新增轻量治理台，聚合媒体文件、Agent 审批、知识候选和 MCP 审计。
- 治理台 MCP 审计补齐详情弹窗，避免“详情”按钮只有前端引用、没有实际函数实现。
- 新增本地 smoke 验收脚本和 GitHub Actions 基础 CI。
- smoke 脚本改为按“客户端缓存 + 云端漫游”语义检查路线图，避免路线图已更新但脚本因固定句子不匹配而误报。
- 更新 `docs/plan.md`，按当前代码事实标记这些能力为 MVP/部分完成。

这不是完整生产化终态。尤其是图谱候选审核目前是治理记录，不会自动反写或删除 GraphRAG 图谱事实；客户端缓存是浏览器 localStorage 最近消息缓存，不是 IndexedDB 本地数据库级缓存。

## 2. Why This Change Was Needed

之前图谱可视化已经能看节点、边、社区、邻域和路径，但缺少“这个实体/关系不确定，交给人审一下”的入口。GraphRAG 很容易受到 LLM 抽取噪声影响，如果没有审核工作台，错误实体和关系只能混在图里继续被使用。

IM 同步方面，WebSocket 能在线推送，但断线、切后台、刷新页面后缺少统一上线同步入口。前端虽然有未读数 localStorage，但没有把服务端最近窗口合并到本地缓存，也没有使用已有 msg-history 的离线索引 RPC。

Phase 9 的前端体验也需要一个轻量治理入口。完整管理后台会很大，本次先把已有接口聚合起来，让用户能在一个地方看到媒体、审批、候选和工具审计。

最后，项目已经有很多服务和前端 JS，缺少一个统一 smoke 脚本会让每轮大改后验证成本过高。本次先补最小验收基线。

## 4. Core Flow After The Change

图谱候选审核：

```text
用户点击知识图谱节点/关系
  -> 前端详情面板点击“提交审核”
  -> api-gateway /knowledge/review-candidates
  -> knowledge-service Kitex RPC
  -> knowledge-service 读取当前用户可见节点/边详情
  -> 写 knowledge_graph_review_candidates
  -> 前端审核列表展示 pending
  -> 用户点击通过/拒绝
  -> knowledge-service 记录 reviewer_id / review_note / reviewed_at
```

上线同步：

```text
WebSocket onopen 或进入主页面
  -> GET /message/sync
  -> msg-core-service 返回会话列表和每个会话最近 N 条消息
  -> 前端按 message_id / client_msg_id 合并本地缓存
  -> GET /message/offline + /message/unread-count
  -> 前端确认离线索引已处理
  -> 刷新会话列表和当前打开会话
```

治理台：

```text
助手侧边栏“治理台”
  -> 媒体文件：file-service 列表 + preview/download
  -> Agent 审批：agent-manager 审批列表 + 通过/拒绝
  -> 知识候选：memory candidates + knowledge graph review candidates
  -> MCP 审计：mcp-gateway trace 列表 + trace detail modal
```

Smoke 验收：

```text
scripts/e2e-smoke.ps1
  -> 检查 plan 状态口径
  -> 检查 Kitex 根目录占位文件
  -> node --check dist/js/api.js
  -> node --check dist/js/app.js
  -> go test ./...
```

## 5. Key Code Concepts

**审核事实与图谱事实分离**

`knowledge_graph_review_candidates` 不直接修改 `rag_entities` 或 `rag_relationships`。它记录“这个图谱事实需要人工判断”。这样不会因为一个审核按钮误删 GraphRAG 数据，也为后续做审核结果反写、实体合并、关系修订留出边界。

**上线同步不是替代 WebSocket**

WebSocket 负责在线实时推送；上线同步负责补偿断线期间可能错过的消息窗口。前端使用 `message_id` 和 `client_msg_id` 去重，避免一条消息既从 WebSocket 来、又从同步窗口来时重复显示。

**本地缓存是读模型**

浏览器 localStorage 最近消息缓存不是消息事实源。真正事实仍在 msg-core-service 的 MySQL。缓存只用于刷新页面、短断线、切会话时更快显示最近消息，后端同步窗口会覆盖和修正它。

**治理台是聚合入口**

治理台没有新建一个巨型 admin-service，而是把已有服务接口聚合到前端：文件、Agent 审批、记忆候选、图谱候选、MCP 审计。完整管理员权限矩阵和成本面板仍是后续工作。

**Smoke CI 是稳定性基线**

当前 CI 不拉 Docker 依赖，不跑完整浏览器 E2E，只做代码和前端语法的最低保障。这个选择是为了让每次提交都能快速发现明显破坏，而不是一开始就引入容易抖动的大型集成测试。

## 6. Important Implementation Details

- 图谱审核提交时，knowledge-service 会先读取当前 viewer 可见的节点/边详情，避免用户提交自己不可见的图谱事实。
- 审核动作只接受 `approve` 或 `reject`，并记录 `reviewer_id`、`review_note`、`reviewed_at`。
- `knowledge-service` 现在需要 MySQL 配置，用于审核候选表；GraphRAG 图谱数据仍从 rag-service 读取。
- 前端 `messageAPI.send` 现在会传 `client_msg_id`，弱网重试时后端幂等键才真正生效。
- `syncAfterOnline()` 做了 3 秒节流，避免 WebSocket 重连抖动时连续打同步接口。
- 当前消息列表同步合并时调用 `renderCurrentMessages(false)`，不会强制把滚动条拉到底。
- 本地消息缓存限制每个会话最近 80 条，避免 localStorage 无限膨胀。
- `scripts/e2e-smoke.ps1` 会检查 Kitex 是否留下根目录 `handler.go` / `main.go` 占位文件。

## 7. How To Verify

建议执行：

```powershell
./scripts/e2e-smoke.ps1
```

也可以拆开执行：

```powershell
go test ./...
node --check dist\js\api.js
node --check dist\js\app.js
```

本轮修正后已重新执行 smoke，覆盖 Go 全量测试、前端 JS 语法检查、关键文档状态检查和 Kitex 根目录占位文件检查。

手工验证路径：

1. 打开知识图谱页面，点击节点或边，提交审核候选。
2. 在右侧“图谱候选审核”里点击通过或拒绝。
3. 断开再恢复 WebSocket，观察聊天头部同步状态 badge。
4. 打开助手侧边栏的“治理台”，检查媒体文件、Agent 审批、知识候选、MCP 审计入口是否能加载。
