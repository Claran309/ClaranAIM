# Change Note: 知识图谱可视化服务

## 1. What Changed

本次补齐了知识图谱可视化的服务边界、HTTP 接口、前端交互页和文档说明。

核心变化是把“GraphRAG 数据构建”和“知识图谱可视化查询”拆成两个职责：

- `rag-service`：继续负责文档解析、chunk、embedding、Hybrid RAG、GraphRAG 实体/关系/社区数据构建。
- `knowledge-service`：负责把 GraphRAG 子图整理成前端可视化需要的图谱视图，包括节点、边、社区、统计信息、节点大小、颜色、节点详情、关系详情和证据展示。

当前已经有 `/api/v1/knowledge/graph`、`/api/v1/knowledge/node/:id`、`/api/v1/knowledge/edge/:id` 三个浏览器入口。前端新增“知识图谱实验室”，支持搜索节点、实体类型过滤、关系类型过滤、社区过滤、一跳/二跳视图、拖拽缩放、点击节点/边查看详情和证据来源。

这是一次功能新增 + 服务边界重构 + 前端可视化增强 + 文档更新。

后续复查中又修复了两个隐藏问题：

- Kitex 生成命令在仓库根目录留下了默认 `main.go`、`handler.go`、`build.sh`、`kitex_info.yaml` 和 `script/bootstrap.sh`，其中 `handler.go` 仍是空 TODO 实现。这些文件已删除，避免污染根包和误导后续编译/索引。
- 图谱节点排序原本发生在 degree 计算之前，导致“按关系密度排序”实际退化为按 score 排序。现在先计算 degree/size/color，再按 degree + score 排序，并补了测试覆盖。
- 前端节点/关系详情原本只带 `query`，没有带当前实体类型、关系类型、社区和跳数过滤。现在详情请求会复用当前图谱过滤条件，避免右侧详情面板显示过滤范围外的邻居和关系。

## 2. Why This Change Was Needed

GraphRAG 不只是“返回一段答案”，它天然会产生实体、关系、社区摘要和证据链。如果只把这些数据藏在 RAG 检索结果里，用户很难理解项目中服务、表、事件、模块之间的关系。

拆出 knowledge-service 的原因是：

- RAG 负责“生成知识”，Knowledge 负责“浏览知识”。
- 可视化查询需要很多展示属性，例如节点大小、颜色、degree、过滤 facet，这些不应该塞进 RAG 检索主链路。
- 未来如果换 Neo4j、NebulaGraph 或独立图数据库，前端接口可以保持稳定。
- api-gateway 不应直接 import 某个微服务的 `internal` 包，所以当前用 `pkg/knowledgeclient` 作为稳定调用契约。

当前已经完成 Kitex 化：`idl/knowledge.thrift` 已生成 `kitex_gen/knowledge`，并新增独立 `cmd/knowledge-service` 进程。api-gateway 通过 `pkg/knowledgeclient.RPCClient` 调用 knowledge-service，knowledge-service 再通过 rag-service RPC 读取 GraphRAG 子图。

## 4. Core Flow After The Change

```text
用户打开知识图谱页面
  -> 前端调用 /api/v1/knowledge/graph
  -> api-gateway KnowledgeHandler 解析 query/types/relations/community/hops/limit
  -> knowledgeclient.RPCClient.GetGraphView
  -> Kitex knowledge-service.GetGraphView
  -> knowledge-service 调用 rag-service GraphRAG 子图查询
  -> knowledge-service 过滤节点/关系/社区
  -> knowledge-service 计算 degree、size、color、stats
  -> 前端用 G6 渲染图谱
  -> 用户点击节点或边
  -> /api/v1/knowledge/node/:id 或 /api/v1/knowledge/edge/:id
  -> 右侧详情面板展示说明、邻居、关系和 evidence
```

如果 G6 CDN 不可用：

```text
前端检测 window.G6 不存在
  -> 使用 SVG fallback
  -> 保留基础节点/边展示和点击详情
```

## 5. Key Code Concepts

**服务边界**

knowledge-service 不负责索引，也不负责 embedding。它只负责查询视图和可视化 DTO。这能防止 RAG 主链路被 UI 展示需求污染。

**稳定客户端契约**

`pkg/knowledgeclient.Service` 是 api-gateway 依赖的边界。当前网关侧实现是 Kitex RPC client；knowledge-service 内部复用同一套视图 DTO 和转换逻辑。

**GraphRAG 增强而非替代 RAG**

知识图谱用于展示实体、关系、社区和证据链；普通 RAG 仍负责语义检索和回答生成。两者共享底层实体/关系数据，但面向不同使用场景。

**可视化属性后端计算**

节点颜色、大小、degree 和关系颜色在后端计算，前端只负责渲染。这让多个客户端可以复用同一套图谱表现规则。

**权限边界**

当前 knowledge-service 读取的是 rag-service 按 viewerID 返回的可见图谱。也就是说，权限裁剪应该发生在底层 GraphRAG 数据读取阶段，knowledge-service 不应越权扩大数据范围。
