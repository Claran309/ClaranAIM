# Change Note: 知识图谱范围与可视化优化

## 1. What Changed

本次主要修复知识图谱页面和 GraphRAG 展示链路的问题：图谱画布改为更接近全屏的主工作区，实体/关系类型压缩成更少、更好懂的中文概念，支持按文档范围查看图谱，并继续过滤 `0`、`10`、`event_id` 这类无意义实体。

这次涉及功能修复、前端体验优化、展示层降噪、测试补充和文档更新。主要文件包括：

- `dist/js/app.js`
- `dist/css/style.css`
- `pkg/knowledgeclient/rag_backed.go`
- `pkg/knowledgeclient/view_test.go`
- `internal/rag-service/service/service.go`
- `internal/rag-service/service/service_test.go`

## 2. Why This Change Was Needed

之前知识图谱虽然能显示，但有几个体验和数据质量问题：

- 画布面积偏小，右侧详情和顶部控件占用太多空间，大图很容易挤成一团。
- 实体类型和关系类型过多，用户需要理解 `DatabaseTable`、`EventTopic`、`PUBLISHES`、`CONSUMES` 等内部枚举。
- 图谱中仍可能出现纯数字、字段名、状态值、文件名等无意义节点。
- 关系边可能出现明显不合常理的组合，例如“数据表调用服务”。
- 从知识文档列表点击“看图谱”时，需要真实按 `document_id` 查询，而不是用标题搜索假装过滤。

新的设计把图谱页面当成分析工作台：默认展示更少但更可读的节点和边，文档范围通过 `document_id` 传到 GraphRAG 查询链路，实体和关系在展示层转成业务用户能看懂的中文分类。

## 3. Files Changed

- `dist/js/app.js`: 调整知识图谱页面结构、默认图谱查询规模、G6 标签显示策略、文档范围选择、节点/关系中文梗概。
- `dist/css/style.css`: 把知识图谱布局改成画布优先，扩大画布宽高，收窄详情栏，压缩顶部说明和工具栏。
- `pkg/knowledgeclient/rag_backed.go`: 在 knowledge-service 展示层过滤无意义实体，压缩实体/关系类型，去重关系边，并给关系说明增加中文兜底。
- `pkg/knowledgeclient/view_test.go`: 增加文档范围透传和脏实体过滤回归测试。
- `internal/rag-service/service/service.go`: 在 RAG 图谱出口根据实体类型过滤明显不合理的关系。
- `internal/rag-service/service/service_test.go`: 增加服务层测试，覆盖数字/字段名节点过滤和不可能关系过滤。

## 4. Core Flow After The Change

```text
前端知识图谱页面
  -> 用户选择文章范围、实体类型、关系类型、邻居深度
  -> api-gateway / knowledge-service
  -> knowledgeclient.GraphQuery(document_id, hops)
  -> rag-service GraphInput(document_id, hops)
  -> rag_relations 按 document_id 查询种子关系
  -> 可选扩展邻居关系
  -> RAG 展示出口过滤噪声节点和不合理关系
  -> knowledge-service 压缩类型、去重、计算颜色/大小/度数
  -> 前端 G6 画布渲染
```

文档范围过滤的关键点是：实体本身是全局归一化的，文档范围不能靠实体表过滤，而要通过 `rag_relations.document_id` 找到某篇文档里的关系，再反查关系两端实体。

## 5. Key Code Concepts

**Document Scope**

`document_id` 表示用户只想看某篇文档中的实体关系。它从前端 select 传入，一路到 `rag-service` 的 `ListGraph`，由 `rag_relations.document_id` 执行真实过滤。

**Display Type Compression**

底层可以继续保存较细的类型，例如 `DatabaseTable`、`EventTopic`、`API`。展示时压缩为 `Service`、`Data`、`Event`、`Interface`、`Concept`，减少用户认知负担。

**Relation Compression**

底层关系如 `PUBLISHES`、`CONSUMES`、`TRIGGERS` 会展示为“事件流”；`READS`、`WRITES`、`STORES` 会展示为“数据流”。这样前端筛选不会被大量近义关系塞满。

**Graph Noise Filtering**

图谱不是越多越好。字段名、状态词、纯数字、文件名、URL 等节点会破坏可读性，所以在 RAG 出口和 knowledge 展示层都做保守过滤。

**Relation Policy**

关系也要看源/目标类型。例如服务写表是合理的，表调用服务通常不合理。`filterGraphForDisplay` 会用实体类型做一次出口检查。

## 6. Important Implementation Details

- 文档范围过滤不使用标题搜索，而是传递 `document_id`。
- 默认图谱查询限制从 `180` 降到 `120`，避免默认视图过载。
- 边数量超过 `18` 时隐藏边标签，只保留颜色和点击详情，减少画布杂乱。
- G6 force layout 增大节点排斥和连线距离，让节点更容易分开。
- 节点详情和关系详情在缺少 LLM 摘要时，会用中文模板生成说明。
- 测试覆盖了 `document_id/hops` 透传、无意义节点过滤、明显不合理关系过滤。
