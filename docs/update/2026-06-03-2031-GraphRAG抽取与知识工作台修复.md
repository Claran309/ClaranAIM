# Change Note: GraphRAG 抽取与知识工作台修复

## 1. What Changed

本次修改修复了知识图谱和 RAG 页面中的几类问题：

- GraphRAG 构建改为优先使用 parent chunk / 章节级内容抽取实体关系，而不是只在碎片化 child chunk 上抽取。
- 会话摘要、会话主题、聊天归档类内容不再进入知识图谱，只保留在 RAG / memory 相关链路中使用。
- 配置了 LLM 图谱抽取器时，不再在 LLM 返回空结果后使用规则抽取兜底，避免把数字、普通例子和无意义词强行变成实体。
- 选中文档查看图谱时，如果该文档历史上没有图谱关系，rag-service 会尝试从已保存的 chunks 按需重建一次图谱。
- Adaptive RAG 判断为 direct answer 时，也会生成当前页面可展示的最终回答，不再把 Router 诊断文本当作答案。
- RAG 页面和知识图谱页面增加“返回知识工作台”入口，知识图谱画布改为更大面积的工作台布局。

这次主要是 bug fix + 体验修复 + GraphRAG 构建策略调整。

## 2. Why This Change Was Needed

原来的 GraphRAG 有两个核心问题。

第一，抽取粒度太碎。系统只拿 child chunk 做实体关系抽取，长文档被切成很多小块后，每个小块缺少章节上下文，模型或规则都很容易抽出局部噪声，或者完全抽不出关系。

第二，规则兜底太积极。即使配置了 LLM 图谱抽取，只要 LLM 返回空实体，系统仍可能落回规则抽取。规则抽取适合兜底识别 `agent-manager-service`、`event_outbox` 这类强模式技术实体，但不适合从普通文章、课件、简历类文档中判断重要概念，所以会产生无意义节点。

新的策略更保守：有 LLM 时相信 LLM 的空结果，不用规则硬凑图；没有 LLM 时才保留最低限度规则抽取。这样图谱可能少一些，但不会轻易乱成一团。

## 3. Files Changed

- `internal/rag-service/service/service.go`: 调整 GraphRAG 抽取候选、会话来源过滤、direct answer 生成、按文档空图谱时的按需重建逻辑。
- `internal/rag-service/dao/dao.go`: `SearchFilter` 增加 `DocumentID`，支持按文档回源读取 chunks。
- `internal/rag-service/service/service_test.go`: 增加会话不建图、父块优先抽取、禁用 LLM 后规则兜底、旧文档按需重建图谱的回归测试。
- `dist/js/app.js`: RAG 诊断信息改为折叠展示，RAG / 知识图谱子页增加返回知识工作台入口。
- `dist/css/style.css`: 知识工作台和知识图谱页面布局调整，图谱画布改为占据更多主区域，并补充按钮 hover / active 动效。

## 4. Core Flow After The Change

文档新入库时：

```text
上传/录入文档
  -> rag-service buildHierarchicalChunks
  -> child chunk 写向量索引
  -> source_type 判断是否允许建图
  -> parent chunk / 高质量 chunk 进入 GraphRAG extractor
  -> LLM 抽取实体和关系
  -> 过滤噪声实体、低可信关系、无证据关系
  -> 写 rag_entities / rag_relations
  -> 重建社区摘要
```

按文档查看旧图谱时：

```text
前端选择某个文档
  -> knowledge-service / rag-service GetGraph(document_id)
  -> 如果该文档没有图谱节点和关系
  -> rag-service 从 rag_chunks 按 document_id 回源
  -> 对已有 chunks 跑一次 buildGraph
  -> 再次查询该文档图谱
  -> 返回节点、关系和社区
```

RAG direct answer 时：

```text
用户提问
  -> Adaptive Router 判断无需检索
  -> resolveUserRouter 找用户/默认小模型
  -> 有模型则生成页面最终回答
  -> 无模型则返回明确的本地兜底回答
```

## 5. Key Code Concepts

**Parent chunk 优先**

parent chunk 保存章节级正文和摘要，适合抽取实体关系。child chunk 更适合检索命中，因为它更短、更精准。GraphRAG 使用 parent chunk，普通检索仍使用 child chunk，这是两种不同的索引目标。

**保守降级**

LLM 图谱抽取器配置后，如果 LLM 返回空结果，系统不再用规则抽取自动补上。这是为了避免“看起来有图，但全是错图”。规则抽取只适合没有 LLM 时的最低限度 fallback。

**source_type 边界**

`conversation`、`chat`、`conversation_summary` 这类来源不进入知识图谱。聊天归档可以进入 RAG 或 memory，但不应该污染文档知识图谱。

**按需重建**

旧文档以前可能已经写了 chunks，但没有实体关系。现在按文档打开图谱时，如果发现空图谱，会从 MySQL chunks 回源尝试重建一次。这不是后台全量重建任务，只是用户查看某个文档时的修复路径。

## 6. Important Implementation Details

- GraphRAG 抽取候选最多取 36 个高质量 parent chunk，避免长文档上传时一次性触发过多 LLM 调用。
- 如果文档没有足够长的 parent / child chunk，系统仍会选取少量非空 chunk，避免短文档完全不触发抽取。
- 会话类 source type 直接跳过 `buildGraph`，因此不会产生“会话摘要”“会话主题”节点。
- RAG direct answer 会优先使用用户配置或默认的小模型；如果模型不可用，会返回一个明确的兜底回答，并提示用户可切换“文档检索”强制查知识库。
- 知识图谱前端仍兼容 G6；没有 G6 时使用 SVG fallback。

```text
5. 在 RAG 页面用“文档检索”问一个短标题式问题，确认仍会强制检索知识库。
```
