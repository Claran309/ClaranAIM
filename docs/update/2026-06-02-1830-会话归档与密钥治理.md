# Change Note: 会话归档与密钥治理

## 1. What Changed

本次更新把前几轮已经做出的 Memory、RAG、MCP 和 Knowledge Graph 能力继续向生产化推进，重点落在三件事：

- `conversation-intelligence-service` 从“能手动归档”的 MVP，升级为带 LLM 提炼器、失败重试、任务状态查询和前端状态页的会话归档服务。
- `settings-service` 对 LLM API Key 和 MCP Secret 增加应用层 AES-GCM 加密存储，浏览器侧继续只看到脱敏状态。
- `docs/plan.md` 按当前代码事实修正状态，尤其把 Knowledge Graph 的实体归一化、社区划分和社区摘要从“未完成”改为“MVP 已有，仍需生产化”。

这次同时包含功能增强、配置变更、IDL/RPC 变更、前端入口变更、测试变更和文档变更。

## 2. Why This Change Was Needed

之前的会话智能归档更像一个“能跑通的归档按钮”：它能把聊天窗口处理成摘要、主题和候选记忆，但失败后缺少可观察状态，调度器也不能自动捞起可重试任务。这样在真实 IM 场景里会很难定位问题：用户只会觉得“我错过了什么”没有更新，但服务端没有一个清楚的任务状态面板。

同时，用户配置自己的 LLM API Key、Rerank Key、MCP Secret 后，明文存数据库是不合理的。当前实现没有直接上 KMS，是因为这是本地开发/单机部署优先的项目阶段；这次先做应用层 AES-GCM 可逆加密，让服务内部能继续解析密钥，同时避免数据库裸明文。

Knowledge Graph 这边，代码已经具备 canonical key 合并、Leiden-like 社区划分和社区摘要持久化。如果计划文档继续写成完全未完成，会误导下一阶段开发。因此本次也严肃修正路线图口径。

## 4. Core Flow After The Change

```text
IM 消息事件 / 用户手动创建归档任务
  -> conversation-intelligence-service 记录活跃会话游标或 DigestJob
  -> Scheduler 扫描到期游标和失败可重试任务
  -> msg-core-service 拉取当前 viewer 可见的消息窗口
  -> filterWindowMessages 做消息 ID / 时间范围裁剪
  -> filterValuableMessages 去掉低价值短噪声
  -> LLMArtifactExtractor 提炼结构化产物
     -> 失败则 FallbackArtifactExtractor 降级规则提炼
  -> MySQL 保存 conversation_summary / decision / task / topic / quote
  -> 摘要和 topic chunk 写入 rag-service
  -> memory_candidate 写入 memory-service pending 区
  -> 更新 DigestJob 状态、重试次数、完成时间或下次重试时间
  -> 前端任务状态页展示归档结果和失败重试入口
```

Settings 密钥保存流程：

```text
用户保存 LLM Profile / MCP Server
  -> api-gateway
  -> settings-service Kitex RPC
  -> settings-service service 层判断 APIKeyAction / SecretAction
  -> SETTINGS_SECRET_KEY 派生 AES-GCM key
  -> 数据库保存 enc:v1:<nonce+ciphertext>
  -> 列表接口只返回 has_api_key / has_secret
  -> runtime / mcp-gateway 解析配置时 service 层解密
```

## 5. Key Code Concepts

**应用层可逆加密**

这里的目标不是替代 KMS，而是让本地部署阶段不要把 API Key 和 MCP Secret 裸写进数据库。`internal/settings-service/service/secrets.go` 使用 AES-GCM，密文带 `enc:v1:` 前缀。没有前缀的旧值会按明文返回，所以旧数据不会因为开启新逻辑立刻不可用。

**密钥脱敏和内部解析分离**

列表接口返回给浏览器的是脱敏 DTO，只表达“是否已配置”。内部服务需要调用模型或远程 MCP 时，走 `ResolveLLMProfile` / `ResolveMCPServers` 这类解析路径，由 settings-service 负责解密。这样前端永远不需要拿回真实密钥。

**会话归档任务状态**

`DigestJob` 不再只是 pending/completed/failed。它现在记录 `retry_count`、`max_retries`、`next_run_at`、`last_attempt_at` 和 `completed_at`。这让调度器和前端能解释“为什么还没成功”“什么时候会重试”“是不是已经超过重试上限”。

**LLM 提炼器与规则 fallback**

LLM 提炼器更适合从聊天里抽取决策、任务、主题和候选记忆，但外部模型可能超时或返回非法 JSON。因此 `FallbackArtifactExtractor` 让主提炼器失败时降级到规则提炼器。效果是质量可能下降，但队列不会因为模型抖动整体停摆。

**权限边界**

归档任务查询和重试都以登录用户作为 `viewer_id`。服务层会检查 job 的 `ViewerID`，用户不能重试或查看别人的归档任务。消息窗口仍从 msg-core-service 读取 viewer 可见历史，不绕过 IM 权限。

**GraphRAG 状态口径**

当前图谱不是“完整生产级 GraphRAG”，但也不是空壳。`rag-service` 已有 canonical key 合并实体、关系表、社区表、Leiden-like 社区分配和社区摘要持久化；后续缺口是候选审核、严格 Leiden 库级实现和专用图数据库评估。

## 6. Important Implementation Details

- `SETTINGS_SECRET_KEY` 为空时走兼容模式，不加密也不解密，便于测试和旧环境临时过渡。
- AES-GCM 密文格式固定为 `enc:v1:`，后续如果接 KMS 或轮换密钥，可以通过版本前缀区分算法。
- 解密失败会返回明确错误，提示检查 `SETTINGS_SECRET_KEY` 是否与保存时一致。
- LLM 提炼器调用 OpenAI-compatible `/chat/completions`，并要求模型只返回 JSON；解析时会从返回文本中截取首尾 `{...}`，兼容模型偶尔包裹说明文字的情况。
- 会话归档失败后，`failJob` 会写入错误原因并计算 `next_run_at`。调度器除了扫描活跃会话，也会扫描 `status=failed && retry_count < max_retries` 的任务。
- 手动重试只允许失败任务，且必须是当前 viewer 自己的任务。
- `filterWindowMessages` 会按 `start_message_id/end_message_id/start_time/end_time` 做二次裁剪。即使 msg-core 当前窗口拉取不够精确，service 层也会尽量保证本次归档边界清晰。
- 前端只展示任务状态和重试入口，不直接暴露内部错误栈或密钥内容。
- `docs/plan.md` 使用 `[x]/[~]/[ ]` 三档状态，避免把 MVP 写成完整生产级能力。

## 7. How To Verify

本次收尾后执行了以下验证：

```powershell
go test ./...
node --check dist\js\api.js
node --check dist\js\app.js
```

也建议针对性阅读或执行：

```powershell
go test ./internal/settings-service/service ./pkg/config
go test ./internal/conversation-intelligence-service/service ./internal/conversation-intelligence-service/handler ./pkg/conversationintelclient
go test ./internal/api-gateway/handler
```

如果要手工验证，可以：

1. 设置 `SETTINGS_SECRET_KEY` 后保存一个 LLM Profile，确认数据库中 API Key 以 `enc:v1:` 开头。
2. 打开系统设置页面，确认 LLM / MCP 列表只显示“已配置密钥”而不回显明文。
3. 创建会话归档任务后，在前端归档状态区域查看任务状态。
4. 人为让 LLM 提炼器配置错误，确认任务失败后有 retry 信息，并可点击重试。
