# Change Note: GraphRAG 图谱增强

## 1. What Changed

本次把 `rag-service` 里的 GraphRAG 从“正则抽关键词 + 共现边”的轻量原型，升级为更接近正式 GraphRAG 的 MySQL MVP。

主要变化：

- 入库时抽取 `Entity` 和 `Relationship` 两类核心图谱对象。
- 实体增加 `canonical_key` 和 `aliases_json`，用于把 `msg-core-service`、`msg core service`、`消息核心服务` 这类同义实体合并到同一个节点。
- 关系增加 `description`、`confidence`、`evidence_chunk_id`，让图谱边能追溯到原始 chunk。
- 图谱查询从简单 `LIKE` 节点搜索，升级为“种子实体 + 1-hop 邻居 + 相关边 + 社区摘要”。
- 社区划分从取实体名前两个字，改为领域启发式社区，例如 `IM 消息链路`、`Agent 事件链路`、`Memory/RAG`、`文件服务`。
- 新增单元测试覆盖实体归一、typed relation 和 1-hop 子图查询。

这是一组后端功能、数据库模型、查询行为和测试变更，主要影响 RAG 知识图谱，不影响前端接口结构和现有 Hybrid Search 主流程。

## 2. Why This Change Was Needed

原来的 GraphRAG 更像“把文档里看起来像实体的词捞出来，然后两两连线”。这种实现能做可视化雏形，但有几个问题：

- 没有实体归一，`msg-core-service` 和 `msg core service` 会变成两个节点，图谱很快碎成一堆重复实体。
- 关系只有 `co_occurs_with`，不能表达 `CALLS`、`WRITES`、`CONSUMES` 等真实系统关系。
- 关系没有证据 chunk，回答时很难回到原文检查依据。
- 查询只返回命中的节点，不能沿关系扩展到相邻实体，因此回答“某个表和哪个服务有关”这类问题时信息不够。
- 社区摘要太粗糙，不像后续 Leiden 社区划分的形态。

新的实现仍然是 MVP，但数据结构已经向正式 GraphRAG 靠拢。后续要把规则抽取替换成 LLM 抽取、把社区划分替换成 Leiden、把 MySQL 替换成 Neo4j/NebulaGraph，都有明确落点。

取舍：

- 本轮没有直接接 LLM 抽取实体/关系，因为文档入库不能被外部模型调用失败阻断。
- 本轮没有引入 Leiden 依赖，因为 Go 服务内直接跑图社区算法会扩大部署复杂度，更合适的做法是后续离线任务读取 MySQL 图谱表，计算社区后写回。
- 本轮保持现有 thrift 图谱接口不变，避免重新生成大量 RPC 代码；新增字段先用于后端存储和检索增强。

## 3. Files Changed

- `internal/rag-service/model/model.go`：为图谱实体、关系和社区增加 canonical、aliases、description、confidence、evidence chunk、key entities 等字段。
- `internal/rag-service/dao/dao.go`：新增按 canonical key 查询实体；图谱查询改为种子实体搜索后扩展 1-hop 子图。
- `internal/rag-service/service/service.go`：重写 GraphRAG 构建逻辑，新增规则抽取器、实体归一、typed relation、证据 chunk 绑定和领域社区划分。

## 4. Core Flow After The Change

入库时：

```text
用户上传文档
  -> rag-service IngestDocument
  -> buildHierarchicalChunks 生成 parent/child chunks
  -> child chunk 写入向量索引
  -> GraphRAG indexing 读取 child chunks
  -> ruleGraphExtractor 抽取实体和关系
  -> canonicalEntityKey 合并同义实体
  -> rag_entities / rag_relations / rag_communities 写入 MySQL
```

查询图谱时：

```text
GET /rag/graph?query=agent_dispatch_records
  -> dao.ListGraph
  -> 搜索 name / summary / aliases_json / canonical_key 得到 seed entities
  -> 查询 source_id 或 target_id 命中 seed 的关系
  -> 拉取 1-hop neighbor entities
  -> 拉取相关 communities
  -> 返回 nodes / edges / communities
```

在 RAG 搜索中：

```text
Adaptive Router
  -> Hybrid Search: Dense + BM25 + RRF
  -> Model Rerank
  -> CRAG / Self-RAG
  -> GetGraph 获取相关实体关系
  -> answer 中附加相关图谱实体
```

注意：GraphRAG 不是替代主 RAG，而是增强上下文。主检索链路仍然是 child chunk 的 Dense + BM25 + RRF + Rerank。

## 5. Key Code Concepts

### Entity

实体是图谱节点。当前支持的类型命名对齐正式 GraphRAG 设计，包括：

- `Service`
- `DatabaseTable`
- `EventTopic`
- `API`
- `Module`
- `Concept`
- `Person`
- `Organization`
- `Product`

在代码里对应 `model.Entity`。新增的 `CanonicalKey` 用于判断两个名字是否指向同一个实体，`AliasesJSON` 用于保存别名。

### Relationship

关系是两个实体之间的有向边。当前关系类型对齐你提出的设计：

- `CALLS`
- `PUBLISHES`
- `CONSUMES`
- `STORES`
- `OWNS`
- `DEPENDS_ON`
- `CONFIGURES`
- `TRIGGERS`
- `READS`
- `WRITES`

在代码里对应 `model.Relation`。新增的 `EvidenceChunkID` 是关键字段，它让关系不只是“模型说有关系”，而是能回到具体 chunk 查看证据。

### Entity Resolution

实体归一化不是简单查名字是否相等，而是先生成 canonical key。

例如：

```text
msg-core-service
msg core service
消息核心服务
```

当前会归一到：

```text
msgcoreservice
```

这样可以避免同一实体因为写法不同被拆成多个节点。

### 1-hop Subgraph

用户搜索某个实体时，只返回这个实体通常不够。现在查询会沿着关系向外走一跳：

```text
agent_dispatch_records
  <- WRITES -
agent-manager-service
```

这样前端图谱和 Agent 回答都能看到“实体和周边系统的关系”。

### Community Summary

社区用于把图谱分章节。当前不是 Leiden，而是规则分组：

- 消息、会话、msg、message -> `IM 消息链路`
- agent、助手、调度 -> `Agent 事件链路`
- rag、memory、milvus、知识 -> `Memory/RAG`
- file、minio、ocr、文件 -> `文件服务`
- 其他 -> `通用知识图谱`

这是后续 Leiden 离线社区划分的占位实现。

## 6. Important Implementation Details

- GraphRAG indexing 只读取 child chunks。这样证据粒度更小，关系边能挂到具体 `evidence_chunk_id`。
- parent/child 分层检索没有被改动。GraphRAG 是增强图谱，不影响现有 parent 返回上下文策略。
- 当前抽取器是 `ruleGraphExtractor`。它通过工程标识符、CamelCase、中文服务/模块词、别名句式和关系动词识别实体关系。
- 抽取器已经被接口化为 `graphExtractor`，后续可以加入 `LLMGraphExtractor`，用小模型按 JSON schema 抽取实体和关系。
- DAO 查询同时匹配 `name`、`summary`、`aliases_json` 和 `canonical_key`，所以用户搜别名也能找到 canonical entity。
- 关系边的 `Relation` 字段使用大写枚举风格，避免前端和后续查询里混用 `co_occurs_with`、`writes`、`写入`。
- thrift 接口暂未扩展 aliases/confidence/evidence_chunk_id。原因是前端当前只需要基本节点和边字段，直接改 thrift 会带来大量生成代码变更；后续做图谱详情面板时再扩展 RPC DTO 更合适。

## 后续升级建议

下一阶段可以按这个顺序继续增强：

1. 新增 `LLMGraphExtractor`，按固定 JSON schema 抽取实体和关系，失败时降级 `ruleGraphExtractor`。
2. 增加实体审核/合并接口，让用户能手动合并错误实体。
3. 增加离线社区任务：MySQL 读 entities + relationships，Python/Go job 跑 Leiden，写回 `rag_communities`。
4. 扩展 thrift DTO，把 `aliases`、`confidence`、`evidence_chunk_id`、`description` 暴露给前端图谱详情面板。
5. 在线查询时并行执行 Hybrid Search、GraphRAG subgraph、community summary search，然后统一 rerank/context selection。
